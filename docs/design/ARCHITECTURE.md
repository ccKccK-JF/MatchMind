# 系统架构

MatchMind 由五个可独立运行的进程组成。外部客户端访问 HTTP API，内部服务使用
版本化 Protobuf/gRPC 契约通信。

```text
HTTP 客户端
    |
    v
api-service :8080
    |-------------|--------------------|-------------------|
    v             v                    v                   v
player-service  matchmaking-service  simulation-service  agent-service
:50051/:8081    :50052/:8082         :50053/:8083        :50054/:8084
                    ^                    |                   |
                    | 完成 Match         |                   |
                    |<-------------------|                   |
                    | 只读工具/受控发布                       |
                    |<---------------------------------------|
                    v
             matching workers（1..N）
```

## 包边界

- `internal/*/domain`：聚合、状态机、值对象和业务不变量；
- `internal/*/application`：通过接口编排用例；
- `internal/*/transport`：把 HTTP/gRPC 请求映射到应用层；
- `internal/*/gateway`：适配其他服务或外部平台；
- `internal/*/repository`：内存、PostgreSQL 和 Redis 实现；
- `internal/platform`：日志、指标、追踪、ID 和通用服务器；
- `proto`：内部服务契约的唯一事实来源；
- `gen/go`：生成的消息和 gRPC 客户端/服务端代码。

领域和应用代码不依赖数据库、gRPC 或消息中间件，基础设施通过接口接入。

## 完整匹配链路

1. Player 服务校验并保存玩家、评分、行为稳定分和英雄熟练度。
2. Matchmaking 创建幂等 Ticket，并按模式、客户端版本、区域分池。未知模式直接拒绝；
   排位使用严格策略，普通更快放宽，训练使用沙盒范围。
3. Worker 以最长等待 Ticket 为锚点，两次批量检查玩家实时资格。玩家服务不可用时
   关闭式失败；新封禁玩家的排队 Ticket 会被取消。
4. 候选窗口随等待时间有界扩展，但客户端版本、玩家资格、开黑完整性和硬延迟上限
   永不放宽。
5. 策略选择器选用 Greedy、Beam 或稳定 A/B 分桶。算法保持开黑队伍完整，为每队
   分配五个唯一位置，并以稳定排序保证确定性。
6. Worker 对所有有容量的区域执行分队优化，根据平均/最大延迟、队间差异、标准差
   和可用服务器数选择区域。质量分由实力、位置、延迟、组队和等待五部分组成。
7. 达到阈值后原子预占全部十个 Ticket。预占成功才创建 Match；失败则不产生半场比赛。
8. 每名玩家按已分配位置选择兼容且熟练度最高的英雄；空熟练度表使用中性值 50。
   英雄、熟练度和行为分进入不可变 Match 快照。
9. 本地分配器预留容量，或 Agones 创建原子 `GameServerAllocation`。成功后 Match
   进入 READY，十个 Ticket 在同一提交边界进入 ASSIGNED。
10. 固定种子的模拟器结合评分、英雄、行为、位置、延迟和组队因素生成赛果。只有
    `ranked_5v5` 执行一次幂等 Elo/Glicko-2 更新。
11. Match 完成时保存过程指标，释放服务器容量，并清除玩家的活跃 Ticket 限制。
12. 质量分析按策略、模式、区域和时间比较预测质量与实际质量；历史回放重建 Ticket
    快照，复用实时模式调优和分队算法，但不写入线上状态。
13. Agent 只能读取队列、策略、质量和回放结果，生成候选策略而不能直接修改实时匹配。
14. 不同审核人通过五项风险检查后审批，管理员才能灰度激活或回滚。

Match 会保存策略版本和游戏模式，因此历史分析不依赖当时进程内的隐藏配置。离线批量
模拟与历史回放都不会修改 Match、Ticket 或评分状态。

## 评分模型

Elo 是兼容默认值，按双方平均评分执行零和更新。配置为 Glicko-2 时，一场 5V5
比赛被视为每名玩家对“对方聚合队伍”的一次评分周期观测，不拆成五场虚构 1V1。
评分、评分偏差和波动率在同一事务中更新，并记录评分算法。两种算法共享 Match 级
幂等边界。

## 并发与一致性

内存仓储对复合状态变化整体加锁。十个 Ticket 的预占和分配要么全部成功，要么全部
失败；活跃玩家索引阻止同一玩家拥有两个有效 Ticket。

生产路径以 PostgreSQL 作为持久化事实来源，以 Redis 作为可重建协调层：

- PostgreSQL 事务、行锁、部分唯一索引和版本号保护持久状态；
- Redis Sorted Set 保存队列顺序，Lua 脚本原子校验并预占十个 Ticket；
- Redis 写入后的 PostgreSQL 冲突会触发补偿释放；
- 启动恢复会释放过期预占并重建缺失队列项。

## Trace ID 与可观测性

API 校验或生成 `X-Trace-ID`，写入上下文和响应头。共享 gRPC 客户端拦截器把它写入
`x-trace-id` 元数据，服务端拦截器恢复上下文，并记录方法、状态码、耗时和 Trace ID。
一次公共请求可跨 Player、Matchmaking、Simulation 和 Agent 保持关联。

各进程暴露 `/health`、`/ready` 和 `/metrics`；核心指标涵盖队列长度、等待时间、
匹配尝试/成功/失败、质量分、预占冲突和 Worker 耗时。

## Agent 安全边界

Agent 网关在编译期固定工具白名单，不提供 Shell、任意 RPC 或 SQL。变更调用同时要求
已审批提案和内部控制令牌。运行输入输出、模型与提示版本、每次工具调用、风险项、
申请人、审核人、灰度参数、激活和回滚全部可审计。`ACTIVATING` 与
`ROLLING_BACK` 过渡态用于处理外部调用中断后的安全重试。
